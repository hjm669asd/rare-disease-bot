# 6.7 调试 LCEL 链路

RAG 系统出现问题时，不应该只看最终答案。

应该逐步检查链路中的中间结果。

## 常见需要调试的内容

- 用户问题是否正确传入。
- Retriever 检索到了哪些文档。
- context 是否包含关键信息。
- prompt 是否符合预期。
- LLM 输出是否遵守格式。

## 为什么要调试

如果最终回答不准确，可能原因有很多：

```text
切分不好 → 检索不到关键 chunk
Embedding 不准 → 相似文档排序错误
Retriever 参数不合适 → 返回内容太少或太杂
Prompt 不清晰 → 模型自由发挥
输出格式约束不够 → 回答结构不稳定
```

## 示例代码

```python
question = "高血压患者什么时候需要及时就医？"

documents = retriever.invoke(question)
print("检索到的文档：")
for document in documents:
    print(document.metadata)
    print(document.page_content)

context = format_docs(documents)
print("拼接后的 context：")
print(context)

prompt_text = prompt.format(context=context, question=question)
print("最终 prompt：")
print(prompt_text)
```

示例输出：

```text
检索到的文档：
{'source': '高血压危险信号'}
高血压患者如果出现明显头痛、胸闷、视物模糊，应及时就医。

拼接后的 context：
高血压患者如果出现明显头痛、胸闷、视物模糊，应及时就医。

最终 prompt：
你是一个智能医疗科普助手...
```

这个结果说明：

- 调试时要先看检索结果，而不是只看最终回答。
- context 和 prompt 是 RAG 质量的关键中间产物。
- 医疗 RAG 更需要保留可检查的中间过程。
