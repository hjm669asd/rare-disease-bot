# 8.1 企业级 RAG 项目架构

前面 1-7 章已经学习了 RAG 的核心能力：文档加载、切分、Embedding、向量库、Retriever、Prompt、LCEL、检索优化和安全检查。

第 8 章开始，我们不再只写单个 Python 脚本，而是把这些能力组织成一个更接近企业项目的“罕见病智能机器人”。

> 重要说明：本章中的罕见病内容只用于 RAG 技术教学和健康科普，不构成真实医疗建议、诊断或治疗方案。

## 为什么要做企业级项目

脚本 Demo 适合学习原理，但真实项目通常需要面对更多问题：

- **前后端分离**：用户通过 Web 页面提问，后端通过 API 提供 RAG 能力。
- **服务化接口**：RAG 不再只是本地函数，而是一个可被调用的 HTTP 服务。
- **配置管理**：模型名称、检索数量、切分参数不能散落在代码各处。
- **会话管理**：用户希望机器人记住本轮对话上下文。
- **来源引用**：医疗回答必须尽量说明依据来自哪里。
- **日志与异常处理**：企业项目需要知道请求是否成功、哪里失败。
- **安全边界**：罕见病问答不能让模型凭空给出诊断或治疗建议。

## 本章项目目标

本章要实现一个教学版企业级 RAG 项目：

```text
用户浏览器
  ↓
静态 WebUI
  ↓ HTTP 请求
FastAPI 后端服务
  ↓
RAG 服务层
  ↓
Retriever 检索罕见病知识库
  ↓
Prompt 约束回答范围
  ↓
通义千问生成回答
  ↓
返回答案、来源和调试信息
```

它不是完整生产系统，但具备企业级项目的基本雏形。

## 推荐项目分层

```text
rare_disease_bot/
  backend/
    app.py              FastAPI 入口
    config.py           配置管理
    schemas.py          请求和响应结构
    rag_service.py      RAG 核心服务
    session_store.py    简单会话历史
  frontend/
    index.html          WebUI 页面
    style.css           页面样式
    app.js              调用后端 API
```

## 每一层负责什么

### 1. WebUI 层

WebUI 负责：

- 接收用户输入。
- 调用后端 `/api/chat` 接口。
- 展示机器人回答。
- 展示来源引用和检索调试信息。

WebUI 不直接调用大模型，也不直接访问向量库。

### 2. API 层

FastAPI 负责：

- 定义 HTTP 接口。
- 校验请求参数。
- 调用 RAG 服务层。
- 把结果转换成 JSON 返回给前端。

API 层不应该写太多 RAG 细节，否则代码会越来越难维护。

### 3. RAG 服务层

RAG 服务层负责：

- 加载罕见病知识库。
- 切分文档。
- 构建 FAISS 向量库。
- 创建 Retriever。
- 组装 Prompt。
- 调用模型生成回答。
- 整理来源和调试信息。

这是项目中最核心的业务层。

### 4. 会话层

会话层负责保存用户的历史对话。

教学版可以先用内存字典实现：

```text
session_id -> 多轮问答历史
```

真实企业系统中，通常会换成 Redis、数据库或专门的会话服务。

## 企业级 RAG 的关键边界

企业级 RAG 不是简单地把脚本放进接口里。

更重要的是明确边界：

- **知识边界**：只根据知识库回答。
- **能力边界**：不能替代医生诊断。
- **接口边界**：前端只调用 API，不接触密钥和模型。
- **配置边界**：参数集中管理。
- **责任边界**：API、RAG、会话、前端各自负责自己的事情。

## 本节小结

第 8 章的核心变化是：

```text
脚本式 RAG
  ↓
服务化 RAG
  ↓
带 WebUI 的前后端分离 RAG 项目
```

从这一章开始，你将把前面学过的 RAG 组件组合成一个更完整的罕见病智能机器人项目。
