# 8.3 后端 API 服务设计

企业级 RAG 项目通常不会让前端直接调用大模型，也不会让用户直接运行 Python 脚本。

更常见的做法是：后端提供 API，前端通过 HTTP 请求调用 RAG 能力。

## 为什么需要 API 服务

前面章节中的脚本通常是这样运行的：

```text
python xxx.py
  ↓
在终端输入或写死问题
  ↓
打印回答
```

企业项目更常见的是：

```text
浏览器 WebUI
  ↓ HTTP
后端 API
  ↓
RAG 服务
  ↓
返回 JSON
```

API 服务让 RAG 能力可以被网页、小程序、企业系统或其他服务调用。

## 推荐接口设计

教学版罕见病智能机器人可以先设计三个接口：

```text
GET /health
POST /api/chat
GET /api/sessions/{session_id}
```

### 1. 健康检查接口

`GET /health` 用于确认服务是否启动。

示例响应：

```json
{
  "status": "ok",
  "service": "rare-disease-rag-bot"
}
```

### 2. 聊天接口

`POST /api/chat` 是最核心的 RAG 问答接口。

示例请求：

```json
{
  "session_id": "demo-user-001",
  "question": "苯丙酮尿症儿童日常饮食需要注意什么？",
  "debug": true
}
```

示例响应：

```json
{
  "session_id": "demo-user-001",
  "answer": "根据资料，苯丙酮尿症儿童需要在医生指导下进行饮食管理，并长期随访。\n\n本回答仅用于健康科普，不能替代医生诊断或治疗建议。",
  "sources": [
    {
      "source": "rare_disease_knowledge.md",
      "disease": "苯丙酮尿症",
      "section": "日常管理"
    }
  ],
  "debug_info": {
    "top_k": 3,
    "retrieved_count": 3
  }
}
```

### 3. 会话查询接口

`GET /api/sessions/{session_id}` 用于查看某个会话的历史记录。

教学阶段可以只返回内存中的历史问答。

## 请求结构为什么要明确

不要让前端随意传任何字段。

建议使用清晰的请求结构：

```text
session_id：当前用户或当前页面的会话编号
question：用户问题
debug：是否返回检索调试信息
```

这样后端可以更容易校验参数，也方便未来扩展权限、用户 ID、知识库 ID 等字段。

## 响应结构为什么要稳定

前端需要根据响应字段渲染页面。

如果后端有时返回字符串，有时返回对象，前端代码会很难写。

推荐固定返回：

```text
answer：最终回答
sources：来源引用
session_id：会话编号
debug_info：调试信息
```

即使没有来源，也可以返回空列表。

## API 层不应该做什么

API 层应该保持简单，不建议把所有逻辑都写在 `app.py` 中。

API 层不应该直接负责：

- 文档切分细节。
- Embedding 创建细节。
- Prompt 拼接细节。
- 会话历史存储细节。
- 来源去重细节。

这些内容应该交给服务层完成。

## 后端调用流程

```text
POST /api/chat
  ↓
校验请求参数
  ↓
读取或创建 session_id
  ↓
调用 RAGService.answer()
  ↓
保存本轮问答历史
  ↓
返回 answer、sources、debug_info
```

## 本节小结

后端 API 是企业级 RAG 的入口。

它的核心目标不是展示复杂代码，而是建立清晰边界：

```text
前端负责交互
API 负责接收和返回
RAG 服务负责智能问答
```
