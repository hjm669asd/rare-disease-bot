# 8.4 RAG 服务分层与配置管理

企业级项目中，RAG 逻辑不能全部写在一个接口函数里。

如果把加载文档、构建向量库、检索、Prompt、模型调用、来源处理都写进 `app.py`，项目很快会变得难以维护。

## 为什么要分层

脚本式 Demo 通常强调“能跑通”。

企业级项目更强调：

- **能维护**：不同功能放在不同模块。
- **能替换**：以后可以替换向量库、模型或检索策略。
- **能调试**：出问题时知道是哪一层的问题。
- **能扩展**：以后可以加入权限、日志、评测、缓存。

## 推荐分层

```text
app.py
  ↓
RAGService
  ↓
Retriever / Prompt / LLM
  ↓
FAISS / DashScope / LangChain
```

每一层只关心自己的职责。

## app.py 的职责

`app.py` 是 FastAPI 入口。

它应该负责：

- 创建 FastAPI 应用。
- 注册接口路由。
- 接收请求。
- 调用服务层。
- 返回响应。

它不应该写大量 RAG 细节。

## rag_service.py 的职责

`rag_service.py` 是 RAG 核心服务。

它应该负责：

- 初始化知识库。
- 构建 Retriever。
- 组织 Prompt。
- 调用大模型。
- 整理来源引用。
- 生成调试信息。

如果以后要从 FAISS 换成其他向量库，主要修改这里。

## config.py 的职责

`config.py` 用来集中管理配置。

例如：

```text
DASHSCOPE_API_KEY
CHAT_MODEL_NAME
EMBEDDING_MODEL_NAME
CHUNK_SIZE
CHUNK_OVERLAP
RETRIEVAL_TOP_K
```

这样做的好处是：

- 参数位置统一。
- 方便不同环境使用不同配置。
- 避免魔法数字散落在代码里。
- 方便文档说明每个参数的作用。

## schemas.py 的职责

`schemas.py` 用来定义请求和响应结构。

例如：

```text
ChatRequest
ChatResponse
SourceItem
DebugInfo
```

这样前端和后端都知道接口字段是什么。

## session_store.py 的职责

`session_store.py` 用来保存会话历史。

教学版可以使用内存字典：

```text
{
  "session-001": [
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
  ]
}
```

真实企业项目中，可以替换为 Redis 或数据库。

## 配置管理流程

```text
.env 文件
  ↓
load_dotenv()
  ↓
config.py 读取环境变量
  ↓
RAGService 使用配置
  ↓
API 对外提供服务
```

## 哪些内容不应该硬编码

建议不要在业务代码中硬编码：

- API Key。
- 模型名称。
- 向量检索 top_k。
- 文档路径。
- chunk_size。
- chunk_overlap。
- 服务端口。

这些内容都应该放到配置文件或环境变量中。

## 本节小结

企业级 RAG 的代码组织要从一开始就保持清晰。

推荐原则是：

```text
接口归接口
服务归服务
配置归配置
结构归结构
会话归会话
```

这样项目从 Demo 扩展到真实系统时，成本会更低。
