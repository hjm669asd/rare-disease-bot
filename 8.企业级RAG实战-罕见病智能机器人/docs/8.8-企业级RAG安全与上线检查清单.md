# 8.8 企业级 RAG 安全与上线检查清单

企业级 RAG 项目不能只关注“能不能回答”。

尤其是罕见病智能机器人，还必须关注安全、可追溯、可维护和可上线。

> 重要说明：医疗 RAG 系统只能用于健康科普和辅助信息查询，不能替代医生诊断或治疗建议。

## 为什么需要上线检查清单

当项目从 Demo 走向应用时，会出现很多新问题：

- API Key 是否泄露。
- 回答是否有来源。
- 资料不足时是否拒答。
- 是否混入错误疾病资料。
- 服务异常时前端是否有提示。
- 用户是否会误以为机器人能诊断。

上线检查清单可以帮助我们逐项排查风险。

## 1. 配置安全

检查内容：

- `DASHSCOPE_API_KEY` 是否只保存在 `.env`。
- 前端代码中是否没有 API Key。
- `.env` 是否不会提交到公开仓库。
- 模型名称、top_k、chunk_size 是否集中配置。

结论：

```text
敏感信息不能出现在前端，也不能硬编码在公开代码中。
```

## 2. 知识库安全

检查内容：

- 知识库是否标明来源。
- 是否避免写入未经确认的治疗建议。
- 是否保留就医提醒。
- 是否能区分不同疾病。
- 是否存在过期或冲突资料。

结论：

```text
RAG 的回答质量上限，首先取决于知识库质量。
```

## 3. 检索质量

检查内容：

- 用户问疾病 A，是否检索到疾病 A。
- 是否混入疾病 B 的资料。
- top_k 是否过大导致噪声增加。
- top_k 是否过小导致资料不足。
- 是否返回来源和章节。

结论：

```text
医疗 RAG 必须检查检索结果，而不是只看最终回答。
```

## 4. Prompt 安全

检查内容：

- 是否要求只根据资料回答。
- 是否要求资料不足时拒答。
- 是否禁止诊断结论。
- 是否禁止个体化治疗方案。
- 是否要求添加医疗安全声明。

推荐安全声明：

```text
本回答仅用于健康科普和技术演示，不能替代医生诊断或治疗建议。如有不适，请及时咨询正规医疗机构专业医生。
```

## 5. API 安全

检查内容：

- 请求字段是否校验。
- 空问题是否拒绝。
- 错误是否返回清晰提示。
- 是否避免把后端异常堆栈直接返回前端。
- 是否有健康检查接口。

教学版可以先做基础校验，真实项目还需要权限认证、限流和审计日志。

## 6. 前端安全

检查内容：

- 页面是否明确显示医疗免责声明。
- 请求失败时是否提示用户。
- 来源信息是否清晰展示。
- 调试信息是否适合展示给当前用户。
- 是否避免让用户误以为系统能确诊。

## 7. 会话安全

检查内容：

- 会话历史是否只保留必要轮数。
- 用户自述是否不会被当成医学事实。
- 服务重启后的历史丢失是否符合预期。
- 真实项目中是否需要隐私保护和数据脱敏。

## 8. 上线前最小检查表

```text
[ ] 后端服务可以启动
[ ] /health 接口正常
[ ] /api/chat 可以返回 answer
[ ] 回答包含医疗安全声明
[ ] 返回 sources 来源信息
[ ] debug_info 能看到检索片段
[ ] 空问题有错误提示
[ ] 前端不会暴露 API Key
[ ] 资料不足时不会编造答案
[ ] README 写清运行方式
```

## 本节小结

企业级 RAG 的目标不是“模型说得像真的”，而是：

```text
回答有依据
资料可追溯
风险可控制
错误可排查
边界说清楚
```

对于罕见病智能机器人，这些原则比炫酷功能更重要。
