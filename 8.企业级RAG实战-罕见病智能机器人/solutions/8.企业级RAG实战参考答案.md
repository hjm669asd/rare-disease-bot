# 第 8 章参考答案：企业级 RAG 实战 - 罕见病智能机器人

## 练习 1：解释企业级 RAG 架构

参考答案：

```text
静态 WebUI：负责用户交互，收集问题并展示回答。
FastAPI 后端服务：负责提供 HTTP API，接收前端请求并返回 JSON。
RAG 服务层：负责组织检索、Prompt、模型调用和来源整理。
Retriever + Prompt + LLM：负责从知识库检索资料，并基于资料生成回答。
罕见病知识库：提供可检索、可追溯的外部医学科普资料。
```

核心思想是：

```text
前端负责交互
后端负责接口
RAG 服务负责智能问答
知识库负责提供依据
```

## 练习 2：设计罕见病知识库字段

参考答案：

可以包含：

- 疾病名称。
- 基础介绍。
- 常见表现。
- 可能病因。
- 检查与诊断提示。
- 日常管理建议。
- 就医提醒。
- 资料来源。

这些字段可以帮助系统更准确地切分、检索和引用资料。

## 练习 3：区分 API 层和 RAG 服务层

参考答案：

1. 接收 `/api/chat` 请求：API 层。
2. 构建 FAISS 向量库：RAG 服务层。
3. 校验用户问题是否为空：API 层，也可以在 schema 中辅助完成。
4. 拼接 Prompt：RAG 服务层。
5. 返回 JSON 响应：API 层。
6. 整理来源引用：RAG 服务层。

API 层应该保持轻量，RAG 细节应该放在服务层。

## 练习 4：解释配置管理

参考答案：

这些内容不建议硬编码，因为：

- API Key 是敏感信息，不能暴露在代码中。
- 模型名称可能根据环境变化。
- `top_k` 会影响检索质量，需要方便调整。
- `chunk_size` 会影响切分效果，需要实验调参。
- 知识库路径可能在开发、测试、生产环境中不同。

集中配置可以让项目更安全、更容易维护。

## 练习 5：理解会话历史

参考答案：

`session_id` 用来标识一次连续对话。

同一个 `session_id` 下，系统可以保存用户和机器人的历史消息。

例如：

```text
第一轮：什么是苯丙酮尿症？
第二轮：它需要长期随访吗？
```

第二轮中的“它”指代不明确。

如果系统读取了第一轮历史，就可以知道“它”大概率指的是“苯丙酮尿症”。

但在医疗场景中，会话历史只用于理解上下文，不能替代可靠知识库。

## 练习 6：来源引用设计

参考答案：

```json
[
  {
    "source": "rare_disease_knowledge.md",
    "disease": "苯丙酮尿症",
    "section": "日常管理"
  }
]
```

这个结构可以让前端清晰展示资料来源。

## 练习 7：前后端交互流程

参考答案：

```text
用户在 WebUI 输入问题
  ↓
点击发送按钮
  ↓
前端 JavaScript 使用 fetch 调用 /api/chat
  ↓
FastAPI 接收请求并校验参数
  ↓
RAG 服务层检索罕见病知识库
  ↓
Prompt 约束模型基于资料回答
  ↓
后端返回 answer、sources、debug_info
  ↓
前端渲染回答、来源和调试信息
```

## 练习 8：医疗安全检查

参考答案：

至少应检查：

- 回答是否包含医疗安全声明。
- 是否只根据知识库资料回答。
- 资料不足时是否拒答。
- 是否返回来源引用。
- 是否检索到了正确疾病。
- 是否混入无关疾病资料。
- 前端是否没有暴露 API Key。
- 空问题是否有错误提示。
- 是否避免给出诊断结论。
- 是否避免给出个体化用药方案。

## 练习 9：判断风险

参考答案：

机器人不能直接给出诊断和用药建议，因为：

- 诊断需要医生结合病史、体征、检查结果综合判断。
- 罕见病症状可能和多种疾病相似。
- 用药需要考虑年龄、体重、检查结果、禁忌证等因素。
- 模型可能生成不准确或不完整的信息。

更安全的回答方式是：

```text
我不能根据当前信息判断你是否患有某种罕见病，也不能提供个体化用药建议。根据资料，如果你有持续不适、发育异常、反复骨折、代谢异常或疑似遗传病相关表现，建议及时到正规医疗机构就诊，由专业医生进行评估和检查。

本回答仅用于健康科普和技术演示，不能替代医生诊断或治疗建议。
```

## 练习 10：项目扩展思考

参考答案：

可以增加：

- 用户登录和权限控制。
- 文档上传和知识库重建。
- Redis 或数据库保存会话历史。
- 检索质量评测体系。
- 日志追踪和审计。
- 接口限流。
- 多知识库管理。
- 混合检索和重排序。
- Docker 部署。
- 后台管理页面。

这些能力可以让教学版项目逐步接近真实企业系统。
